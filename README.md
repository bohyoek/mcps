## 1. 프로젝트 목표

**약 3년 뒤(2029년경) 서울에서 카페를 개업한다고 가정하고, 후보 상권을 분석해 그 결과를 약 2분짜리 영상으로 만든다.**

- 지역: **서울 시내로 확정** — 매출 데이터(서울시 상권분석서비스)가 서울만 제공되기 때문
- 후보 상권: **메인 = 용산 신용산역·용리단길 일대**, **비교 = 성수동 연무장길 일대**
  - 용산: "용산국제업무지구 개발을 앞두고 지금 들어가면 3년 뒤 효과를 누릴 수 있을까?"
  - 성수: "이미 뜬 상권은 3년 뒤 어떻게 되나?" — 과포화·임대료 급등의 비교 사례

- 결과물: 2분(±15초) 내외의 16:9 영상 1편 (MP4)
- 인원: **4명** — A·B·C는 분석을 **동시에(병렬로)** 하고, 영상은 통일성을 위해 **D가 처음부터 끝까지 혼자** 만든다
- 데이터: **서울 열린데이터광장 OpenAPI**(각자 인증키 발급)를 메인으로 사용 — [4. 데이터 출처](#4-데이터-출처) 참고
- 핵심 질문: *"지금이 아니라 3년 뒤에도 이 상권에서 카페가 살아남을 수 있을까?"*

## 2. 진행 순서와 병렬 구조

```
[0단계 · 함께 20분]  역할·폴더 규칙 합의
        │
        ├──▶ [1단계 · 병렬] 👤A 수요   👤B 경쟁   👤C 비용·3년 뒤   👤D 디자인·스토리보드·오프닝
        │         A·B·C: 자기 폴더에서 수집 → 분석 → 정리된 데이터 + 핵심 메시지 전달
        │
[2단계 · 함께 15분]  각자 핵심 숫자 3개 공유 → 결론(추천/조건부/비추천) 합의
        │
[3단계 · D 집중]  D: 전체 대본 → 차트·장면 제작 → 내레이션 → 최종 mp4
        │         A·B·C: D의 질문 대응, 수치·출처 검수, 발표 준비
        │
[4단계 · 함께]  최종 시청 → 수정 → main에 합치기
```

**역할 원칙:** A·B·C는 **"재료"(정리된 데이터, 숫자, 메시지)** 만 넘기고, 차트 디자인·대본·영상은 **D가 한 번에** 만듭니다. 색·폰트·말투·차트 스타일이 하나로 통일됩니다.

**병목 줄이기:** 3단계에서 D에게 일이 몰리므로,
- D는 1단계 동안 디자인 시스템(색·폰트·차트 스타일), 스토리보드, 오프닝·지역 소개 장면을 **미리 끝내 둡니다**.
- A·B·C는 [5. 결과물 약속](#5-결과물-약속-인터페이스) 형식을 정확히 지켜서, D가 데이터를 다시 정리할 필요가 없게 합니다.
- A·B·C는 먼저 끝난 사람부터 D에게 넘깁니다 (2단계까지 모아 두지 않기).

**기다려야 하는 지점**
1. 0단계: 역할이 정해져야 모두 시작할 수 있음 (분석 범위는 `docs/region.md`에 확정됨)
2. 2단계: 결론은 A·B·C의 결과가 다 나와야 정할 수 있음
3. 3단계: 영상 완성은 D 혼자 하므로 시간이 가장 많이 걸림 — 일정에서 D 몫을 넉넉히 잡기

### 0단계에서 정할 것 (함께)

- [x] 후보 상권: 용산(메인) vs 성수(비교) — [1. 프로젝트 목표](#1-프로젝트-목표) 참고
- [x] 분석 범위 확정 — **행정동 단위**: 용산 = 한강로동, 성수 = 성수2가1동 + 성수2가3동 ([`docs/region.md`](docs/region.md))
- [ ] C가 용산국제업무지구 등 개발 계획의 **최신 일정**을 뉴스로 확인 (지연 여부가 결론에 큰 영향)
- [ ] 분석 범위 — 반경(300m 또는 500m), 기준 시점(올해), 목표 시점(2029년)
- [ ] 영상 톤 — 색상 2~3개, 폰트, 내레이션 목소리 (D가 제안)
- [ ] 각자 역할 배정, GitHub Collaborator 초대 확인

## 4. 데이터 출처

### 서울 열린데이터광장 API 키 설정 (각자 1번)

1. 서울 열린데이터광장에서 발급받은 **일반 인증키**를 준비합니다.
2. **가장 쉬운 방법:** 쓰고 있는 LLM(에이전트)에게 이렇게 말합니다.
   > "내 서울 API 키는 `발급받은키`야. README대로 `.env`에 저장해 줘."

   에이전트가 레포 루트에 `.env`를 만들고 아래 한 줄을 넣습니다 (직접 만들어도 됩니다):
   ```
   SEOUL_OPENAPI_KEY=발급받은키
   ```
3. `.env`는 `.gitignore`에 들어 있어 커밋되지 않습니다. **키를 코드·README·커밋 메시지·단톡방 공개글에 쓰지 마세요** (퍼블릭 레포입니다).
4. 호출 형식: `http://openapi.seoul.go.kr:8088/{키}/json/{서비스명}/{시작}/{끝}/` (한 번에 최대 1,000건)
   - 서비스명 앞의 필터 인자는 무시되는 경우가 많으니, 1,000건씩 받아서 `docs/region.md`의 **행정동 코드**로 걸러 씁니다.
   - 예시 코드: [`parts/a-demand/analysis.py`](parts/a-demand/analysis.py)

### 주요 API (서울시 상권분석서비스, 행정동 단위)

| 서비스명 | 내용 | 주로 쓰는 사람 |
|---|---|---|
| `VwsmAdstrdFlpopW` | 길단위인구(유동인구) — 총량, 시간대, 요일, 연령대, 성별 | A |
| `VwsmAdstrdStorW` | 점포 — 점포 수, 개·폐업, 프랜차이즈 (업종 코드 `CS100010` 커피-음료) | B |
| `VwsmAdstrdSelngW` | 추정매출 — 업종별·시간대별·요일별 매출 | C |

> 세 서비스 모두 2026-11-14에 실제 호출로 확인했습니다. 점포(약 77만 건)·매출(약 38만 건)은 전 업종·전 행정동이라 양이 많으니, 1,000건씩 받으면서 바로 행정동 코드와 업종 코드(`CS100010`)로 걸러 저장하세요.

## 5. 결과물 약속 (인터페이스)

D가 데이터를 다시 정리하지 않고 바로 영상에 쓸 수 있도록, A·B·C는 **아래 형식 그대로** 자기 폴더에 결과를 둡니다.
차트를 예쁘게 만들 필요는 없습니다 — 디자인은 D가 합니다.

```
parts/a-demand/              (b-competition, c-cost-future도 같은 구조)
├── findings.md              # 아래 템플릿
├── SOURCES.md               # 출처 URL + 수집 날짜
├── for-video/               # ★ D에게 넘기는 데이터: 차트 1개당 CSV 1개 (작고 깔끔하게)
│   └── 01_시간대별_유동인구.csv
├── draft-charts/            # 확인용 초안 차트 (디자인 신경 X)
├── data/                    # 내려받은 원본·중간 데이터 (작은 파일만)
└── analysis.py (또는 .ipynb) # 분석 코드
```

**`for-video/` CSV 규칙:** UTF-8, 첫 줄은 한글 열 이름, 단위는 열 이름에 표기(예: `유동인구(명·분기누적)`, `유동인구(명/ha·밀도)`), 차트 하나에 필요한 행만.

**`for-video/UNITS.md` 필수:** 파일마다 단위, 뜻, 영상 화면에 쓸 표기 예시, 기준 시점을 표로 적어 D에게 넘깁니다. 특히 **총량(명)과 밀도(명/ha), 비율(%)** 처럼 단위가 다른 숫자가 섞이면 결론이 달라 보이므로 꼭 구분해 적습니다. (예시: [`parts/a-demand/for-video/UNITS.md`](parts/a-demand/for-video/UNITS.md))

**`findings.md` 템플릿**

```markdown
# [A 수요] 한 줄 결론
예: 평일 출근 시간대 유동인구가 구 평균의 1.8배 — 테이크아웃 수요 충분

## 핵심 숫자 3개
1. ...
2. ...
3. ...

## 3년 뒤 전망
- ...

## 영상에서 꼭 전하고 싶은 메시지 (1~2문장, 대본은 D가 씀)
...

## D에게 넘기는 데이터
- for-video/01_xxx.csv — 무엇을 보여주는 데이터인지, 추천 차트 형태(막대/선/지도 등)
```

- 숫자는 **출처가 있는 것만** 씁니다. 추정치는 "추정"이라고 표시합니다.

## 6. MCP 실습 가이드

| MCP 서버 | 용도 | 주로 쓰는 사람 |
|---|---|---|
| Filesystem (`@modelcontextprotocol/server-filesystem`) | 데이터·차트 파일 읽고 쓰기 | 모두 |
| Fetch (`mcp-server-fetch`) | 서울 열린데이터 API, 웹페이지, Overpass API 가져오기 | A, B, C |
| Playwright (`@playwright/mcp`) | 브라우저로 golmok 화면 조회(임대시세 등), 지도 캡처, HTML 영상 녹화 | 모두 |
| DuckDuckGo 검색 (`duckduckgo-mcp-server`) | 개발 계획·뉴스 검색 | C |

- **서울 API는 별도 MCP 없이** Fetch MCP나 Python으로 바로 부릅니다 (주소에 키만 넣으면 JSON이 옴). 원하면 상권분석용 커뮤니티 MCP([trade-area-mcp](https://github.com/Sejin-Koo/trade-area-mcp))를 같은 키로 써 봐도 됩니다 (미검증).
- GitHub 작업은 MCP 대신 **`git` 명령어**로 합니다.
- 패키지 이름·설정법은 바뀔 수 있으니 **실습 당일 안내나 공식 문서를 우선**하세요.

### 연결 예시

**Claude Code**

## 8. 협업 규칙

- **각자 자기 폴더만 수정**합니다 (A·B·C는 `parts/자기폴더/`, D는 `video/`). 그래서 충돌이 거의 나지 않습니다.
- 공통 파일(README 등)을 바꿀 땐 단톡방에 먼저 말하기
- 브랜치 이름: `a/demand`, `b/competition`, `c/cost-future`, `d/video`
- 중간 결과도 자주 push하고, 다 되면 Pull Request로 `main`에 합치기 (`main`에 직접 push 금지)
- 100MB 넘는 파일(원본 영상 등)은 올리지 말고 공유 드라이브 링크를 남기기
- 레포에 push하려면 레포 주인이 Settings → Collaborators에서 GitHub 아이디를 초대해야 합니다

## 9. 보안·윤리 규칙

- API 키는 **각자 `.env`에만** 두고 절대 커밋하지 않습니다. 실수로 올렸다면 바로 조원에게 알리고 키를 재발급합니다.
- 개인정보(실명, 전화번호, 사람 얼굴 사진)는 수집·업로드하지 않습니다.
- 사이트에 무리가 가는 대량 자동 수집은 하지 않고, 제공되는 파일 다운로드를 우선합니다.
- 모든 수치에 출처와 날짜를 남기고, 영상 마지막에 출처를 표기합니다.

## 🤖 LLM 작업 지침

이 README를 읽은 LLM은 다음 순서로 도와주세요.

1. **역할 확인:** 사용자가 A(수요) / B(경쟁) / C(비용·미래) / D(영상 PD) 중 누구인지 먼저 묻는다. 후보 상권은 **용산 신용산역·용리단길(메인)과 성수동 연무장길(비교)** 로 정해져 있으니, 모든 분석을 두 곳 비교로 진행한다(`docs/region.md`의 행정동 기준: 한강로동 vs 성수2가1동+성수2가3동). 다른 지역으로 넓히지 않는다. 정해지지 않았다면 0단계 체크리스트를 함께 채운다.
2. **환경 확인:** 사용하는 LLM 도구와 연결된 MCP 서버를 확인하고, 부족하면 6번 예시로 연결을 돕는다.
3. **자기 범위만:** 사용자의 역할에 해당하는 폴더(`parts/...` 또는 `video/`)에서만 파일을 만들고 수정한다. 다른 역할의 폴더는 읽기만 한다.
4. **데이터와 API 키:** 4번의 서울 열린데이터 API를 우선 쓴다. 접근 제한을 우회하지 않는다.
   - 레포 루트 `.env`에 `SEOUL_OPENAPI_KEY`가 없으면 사용자에게 키를 달라고 한다.
   - 사용자가 키를 주면 **레포 루트 `.env`에 `SEOUL_OPENAPI_KEY=키` 한 줄로 저장**한다(이미 있으면 그 줄만 바꾼다). 저장 후 `git check-ignore .env`로 커밋 제외인지 확인하고, 키로 1건만 호출해 작동하는지 확인한다.
   - 코드에서는 키를 항상 `.env`에서 읽는다. 키 값을 코드·다른 파일·커밋 메시지·PR·답변에 다시 쓰지 않는다. 커밋 전에 키 값이 스테이징된 파일에 없는지 확인한다.
   - `for-video/`에 CSV를 만들면 **`UNITS.md`에 단위·뜻·화면 표기·기준 시점**을 함께 적는다.
5. **약속된 형식:** A·B·C라면 5번의 폴더 구조와 `findings.md` 템플릿을 그대로 따르고, 차트 디자인·대본·영상은 만들지 않는다(그건 D 몫). D라면 영상 전체를 혼자 만들며 7번 장면표와 폴더 구조를 따르고, 아직 데이터가 없는 장면은 임시 숫자로 자리를 잡아 둔다.
6. **사실만:** 숫자를 지어내지 않는다. 모든 수치는 `SOURCES.md`에 URL과 수집 날짜를 남기고, 추정치는 "추정"이라고 표시한다.
7. **3년 뒤 관점:** 현재 수치와 함께 2029년경의 변화(추세, 개발 계획)를 꼭 포함한다.
8. **작게, 자주:** 한 단계씩 끝내고 결과를 보여 준 뒤 다음으로 넘어간다. 역할 브랜치에서 커밋하고, push 전에는 사용자에게 확인받는다. `main`에 직접 push하지 않는다.
