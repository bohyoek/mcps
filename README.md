## 1. 프로젝트 목표

**약 3년 뒤(2029년) 서울에 베이커리를 연다고 가정하고, 창업 기획을 혼자 완성해 약 2분짜리 모션그래픽 영상으로 만든다.**

```
① 조사  →  ② 논리 구조  →  ③ 시나리오  →  ④ 모션그래픽
(데이터)     (결론과 근거)     (장면별 대본)     (HTML 영상 → mp4)
```

- **개별 과제:** 조사부터 영상까지 **한 사람이 전부** 합니다.
- 업종: **베이커리(빵집)** — 빵·디저트를 굽고 파는 가게가 중심. **베이커리 카페가 아님**
  - 좌석·음료로 매출을 내는 카페형 기획은 하지 않는다. 음료는 있어도 곁들이는 정도
  - 서울시 상권분석서비스 업종 코드: **`CS100005` 제과점**
- 지역: **서울 시내** — 매출·점포 데이터(서울시 상권분석서비스)가 서울만 제공되기 때문
- 기획에 꼭 들어갈 4가지

  | 번호 | 항목 | 질문 |
  |---|---|---|
  | 1 | **입지선정** | 서울 공공데이터로 볼 때, 어느 동네에서 장사하는 것이 **가장 합리적**인가? |
  | 2 | **인테리어 컨셉** | 그 동네 2029년 손님에게 맞는 매장은 어떤 모습인가? |
  | 3 | **메뉴구성** | 무엇을 얼마에 팔고, **무엇으로 손님을 끌어올 것인가(시즌 한정 메뉴)**? |
  | 4 | **손익 시뮬레이션** | 2029년 기준으로 한 달에 남는 돈은 얼마인가? 언제 투자금을 회수하나? |

- 결과물
  - 2분(±15초) 내외의 16:9 **모션그래픽 영상** 1편 (MP4) — 내레이션으로 **결론부터** 전달
  - 요약 웹페이지 1장 — 보는 사람이 **30초 안에 핵심**을 파악

## 평가 기준 (모든 작업은 이 5가지를 채우도록 진행)

| # | 기준 | 평가 내용 | 이 프로젝트에서 지킬 것 |
|---|---|---|---|
| 01 | **지표 설계의 논리성** (Metrics) | 성장 상권을 판단하는 지표와 가중치가 MECE하게 설계되고, 지표 간 정합성이 확보됐는지 | 1번 입지선정을 **점수 모델**로 한다: 지표를 겹치지 않고 빠짐없이 4대 축으로 묶고, 가중치 합 100, 같은 방향(높을수록 좋음)으로 정규화. 서로 겹치는 지표를 이중으로 세지 않는다 |
| 02 | **근거의 구체성** (Evidence) | 주장마다 출처·기간·단위가 명시된 근거가 있고, 그 근거가 사실로 확인되는지 | 모든 숫자에 **(출처, 기간, 단위)** 를 붙인다. 예: `제과점 점포 수 12개 (서울시 상권분석서비스, 2026Q2, 개)`. 링크를 실제로 열어 확인한 값만 쓴다 |
| 03 | **인사이트** (Insight) | 데이터에서 클라이언트가 예상하지 못한 발견을 도출해 "와우"를 이끌어내는지 | 단계마다 `findings.md`에 **"의외의 발견"** 을 1개 이상 적는다 — 상식과 반대되거나 숫자로 처음 드러난 사실. 영상·웹페이지의 핵심 장면으로 쓴다 |
| 04 | **컨셉의 일관성** (Concept) | 상권 분석에서 타깃, 공간, 메뉴, 차별화, 손익까지 하나의 논리로 이어지는지 | `story/logic.md`에 **입지 → 타깃 → 공간 → 메뉴(시즌 한정) → 차별화 → 손익**을 한 줄씩 잇고, 각 단계가 앞 단계의 어떤 근거에서 나왔는지 적는다. 연결이 끊기면 그 단계를 고친다 |
| 05 | **전달력** (Delivery) | 2분 영상이 내레이션으로 결론부터 전하고, 웹페이지가 30초 안에 핵심을 보여주는지 | 영상 첫 15초에 **결론(동네·컨셉·월 이익)** 을 먼저 말한다. 장면마다 **보여 줄 주인공은 하나**. 웹페이지는 첫 화면에 결론 한 줄 + 핵심 숫자 3개 |

## 2. 핵심 원칙: "지금"이 아니라 "2029년"을 본다

이 기획은 **3년 뒤에 문을 여는 가게**입니다. 그래서 **지금 잘나가는 것 자체는 근거가 되지 않습니다.**

| ❌ 근거로 쓰지 않는 것 | ✅ 근거로 쓰는 것 |
|---|---|
| "지금 핫한 동네라서" (예: 성수동처럼 현재 뜬 상권) | 2029년 전후로 **확정된** 변화: 신규 역·노선 개통, 아파트 입주, 오피스 준공, 재개발 일정 |
| "지금 유행하는 디저트를 2029년에도 팔겠다" | 유행이 **생기고 꺼지는 패턴**(주기, 가격대, 퍼지는 경로)을 분석해 만든, 2029년에도 통하는 **한정 메뉴 전략** |
| 올해 임대료·재료비를 그대로 손익에 넣기 | 올해 값에 **과거 상승률을 적용해 2029년 값으로 환산**한 숫자 |
| 지금 매장 수만 보고 "경쟁이 적다/많다" | 개업·폐업 **추세**로 본 2029년 경쟁 전망 |

- 현재 데이터는 **출발점(기준값)과 추세·패턴 계산용**으로만 씁니다.
- 모든 결론에 **"2029년에 왜 그런가"** 를 한 줄로 붙입니다.
- 일정이 아직 확정되지 않은 계획은 "미확정"으로 표시하고, 그것 하나에 결론을 걸지 않습니다.
- **환산 규칙은 처음에 하나 정해 두고** 끝까지 같은 방식으로 씁니다. 예: "최근 5년 연평균 상승률을 2029년까지 그대로 적용"

## 3. 진행 순서

입지를 고르려면 **어떤 가게를 열지(컨셉·매장 규모·비용)** 를 먼저 대략 알아야 하고, 컨셉을 다듬으려면 **어느 동네인지** 알아야 합니다. 그래서 **선행조사로 컨셉 후보를 먼저 잡고 → 입지에서 돈 계산까지 함께 보고 → 컨셉을 확정**하는 순서로 갑니다.

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━ ① 조사 ━━━━━━━━━━━━━━━━━━━━━━━━━━━
[0] 준비         API 키 저장, MCP 연결, 2029년 환산 규칙 정하기
 │
[0] 선행조사      베이커리 시장 흐름, 화제 디저트 주기 분석
 │               → 컨셉 후보 2~3개 + 각각의 "표준 매장 모델"
 │                 (면적, 인테리어·설비비, 가격대, 주 고객)
 ▼
[1] 입지선정      서울 공공데이터 API로 후보 동네 비교
 │               수요·미래 변화·경쟁 + 임대료·손님 수·동네 매출·면적·초기 비용
 │               → "어느 동네에서, 어떤 컨셉으로 하는 게 가장 합리적인가" 1곳 확정
 ▼
[2] 인테리어 컨셉  확정 동네의 2029년 손님에게 맞춰 컨셉·공간 확정
[3] 메뉴구성       주변 상권 가격 비교 + 시즌 한정 메뉴 전략
 ▼
[4] 손익 시뮬레이션 1~3번 값을 모아 2029년 월 손익
 │   └─ 안 맞으면 → 3번 가격·2번 면적 조정, 또는 1번 다른 후보로
━━━━━━━━━━━━━━━━━━━━━━━━━━━ ② ~ ④ ━━━━━━━━━━━━━━━━━━━━━━━━━━━
[5] 논리 구조      결론 1줄 → 근거 3개 → 데이터 (story/logic.md)
[6] 시나리오       장면별 시간·내레이션·화면·데이터·모션 스타일 (story/scenario.md)
[7] 모션그래픽     장면을 HTML 모션으로 만들고 녹화 → mp4, 웹페이지
```

## 4. ① 조사 — 단계별 할 일

### 0. 선행조사 — `parts/0-research/`
- **베이커리 시장 흐름:** 제과점 점포 수·매출의 서울 전체 추세, 동네 빵집 vs 프랜차이즈 비중 변화
- **화제 디저트 주기 분석:** 최근 디저트 붐의 흐름 — 예: **두쫀쿠(두바이 쫀득쿠키) → 버터떡 → 창억떡 → 한정선** 등
  - 메뉴마다: 뜬 시기, 정점까지 걸린 기간, 꺼지기까지 기간, 가격대, 퍼진 경로(SNS·방송·특정 가게), 왜 사람을 끌었는지(식감·모양·희소성·지역색)
  - 출처: 뉴스 기사, 검색량 추이(네이버 데이터랩·구글 트렌드 웹 화면)
  - 목표는 메뉴 하나를 고르는 게 아니라 **"인기 메뉴의 공식"** 과 **유행 주기** 를 찾는 것 → 3번 메뉴 전략의 근거
- **컨셉 후보 2~3개**와 각각의 **표준 매장 모델**
  - 예: "출근길 테이크아웃 식사빵", "동네 가족용 식빵·케이크", "화제 디저트 전문 소형 매장"
  - 컨셉마다: 주 고객, 매장 면적(평), 인테리어·설비비(추정), 가격대, 잘 맞는 동네 조건
- **1번에 넘길 값:** 컨셉별 표준 매장 모델 (`for-pnl.csv` 형식)

### 1. 입지선정 — `parts/1-location/`
- **서울 공공데이터 API**로 후보 동네(행정동)를 비교해 **최종 1곳 + 그곳에 맞는 컨셉**을 고른다
- "합리적" = 수요가 크고 늘어나는 곳이면서, **그 컨셉으로 장사했을 때 돈이 남는 곳**
- **지표 4대 축 (MECE)** — 축끼리 겹치지 않고, 합쳐서 "2029년에 이 동네에서 이 빵집이 잘되나"를 빠짐없이 설명하도록

  | 축 | 묻는 것 | 지표 예시 (모두 2029년 기준 환산) |
  |---|---|---|
  | **수요** | 빵 살 사람이 늘어나나? | 주거인구·가구 수 증감률, 아침·저녁 시간대 유동인구 추세, 주 고객 연령대 비중 |
  | **미래 변화** | 2029년 전후로 확정된 변화가 있나? | 입주 예정 세대 수, 신규 역·노선, 오피스 준공 (확정된 것만) |
  | **경쟁** | 빵집이 버틸 자리가 있나? | 인구 대비 제과점(`CS100005`) 수, 개업·폐업률 추세, 프랜차이즈 비율 |
  | **수익성** | 남는 장사가 되나? | 동네 제과점 점포당 추정매출, 예상 하루 손님 수, 2029년 임대료 × 면적, 인테리어·설비비 회수 부담, 매출 대비 임대료 비율 |

- **점수 계산 규칙**
  - 각 축에 지표 1~3개, 가중치는 축별로 정하고 **합계 100**. 가중치를 정한 이유를 한 줄씩 적는다
  - 지표는 후보끼리 비교할 수 있게 **정규화**(예: 0~100점)하고, "낮을수록 좋은" 지표(경쟁, 임대료)는 방향을 뒤집는다
  - **정합성 점검:** 같은 현상을 두 번 세는 지표가 없는지(예: 유동인구와 손님 수), 축 안의 지표가 서로 모순되지 않는지 확인
  - 가중치를 조금 바꿔도 1등이 그대로인지 **민감도**를 한 번 확인한다
  - 수익성 축은 0번의 **컨셉별 표준 매장 모델**로 계산한다 (동네 × 컨셉 조합으로 비교 가능)
- 결과: 최종 동네 1곳 + 컨셉, 선정 이유, 후보 비교표, `scoring.csv`(지표·가중치·원값·점수)
- **4번에 넘길 값:** 2029년 예상 월 임대료(평당), 하루 예상 손님 수와 근거, 동네 제과점 평균 매출

### 2. 인테리어 컨셉 — `parts/2-interior/`
- 1번에서 고른 컨셉을 확정 동네의 **2029년 주 고객층**(연령, 가구 형태, 방문 시간)에 맞춰 다듬는다
- 매장 형태: 테이크아웃 위주 / 소규모 진열 판매 등 (카페형 좌석 중심 X)
- 면적(평), 동선(진열대·계산대·주방 비율), 분위기·색·재료 키워드
- 결과물: 컨셉 한 줄, 무드보드, 간단한 평면 배치 그림
- 이미지는 **직접 만든 것(AI 생성 포함)이나 무료 라이선스 이미지**만 쓰고, 출처를 남긴다
- **4번에 넘길 값:** 확정 면적, 인테리어·설비 비용(추정)

### 3. 메뉴구성 — `parts/3-menu/`
- **가격·원가율·객단가:** 주변 상권(확정 동네와 인근) 빵집의 가격대와 비교해 정한다
  - 대표 메뉴 3개 + 전체 메뉴 10~20개, 가격, 하루 생산량
  - 메뉴별 **원가율**(재료비 ÷ 가격). 재료비는 밀가루·버터·계란 등 주요 재료 가격 추세로 2029년 값 추정
  - **객단가**(손님 1명이 쓰는 돈) 추정
- **시즌 한정 메뉴 전략:** 0번의 디저트 주기 분석을 바탕으로
  - **시즌 한정 메뉴**(손님을 처음 끌어오는 메뉴) / **기본 메뉴**(매일 사러 오게 하는 메뉴)로 역할을 나눈다
  - 유행 하나에 기대지 않고, 주기에 맞춰 **시즌 한정 메뉴를 교체하는 방식**(예: 몇 개월마다 한정 메뉴)을 정한다
  - 개업 시점(2029년) 첫 시즌 한정 메뉴 후보와, 그것이 "공식"의 어떤 조건을 채우는지
- **차별화:** 1번에서 본 동네 경쟁 빵집들과 무엇이 다른지 한 줄로 정리하고, 그 차별점이 공간·메뉴·가격에 어떻게 드러나는지 적는다
- **4번에 넘길 값:** 메뉴별 가격·원가율, 객단가, 시즌 한정 메뉴의 매출 비중 가정

### 4. 손익 시뮬레이션 — `parts/4-pnl/`
- **2029년 기준** 월 손익표와 투자 회수 기간
  - **초기 투자:** 보증금, 권리금(있다면), 인테리어, 제빵 설비, 초도 재료
  - **매출:** 하루 손님 수 × 객단가 × 영업일
  - **비용:** 재료비(원가율), 임대료, 인건비(2029년 최저임금 추정), 공과금, 카드수수료, 기타
  - **결과:** 월 영업이익, 손익분기 하루 판매량, 투자 회수 개월 수
- **시나리오 3개:** 비관 / 기본 / 낙관 — 손님 수, 원가율, **시즌 한정 메뉴가 뜨는지 여부**를 바꿔서
- 입력값은 0~3번 폴더의 `for-pnl.csv`에서 읽는다
- 모든 2029년 값에 **어떻게 환산했는지**(기준 연도 값, 적용한 연평균 상승률)를 적는다

## 5. ② 논리 구조 → ③ 시나리오

### ② 논리 구조 — `story/logic.md`
조사가 끝나면 영상·웹페이지에 들어갈 **주장의 뼈대**를 먼저 세웁니다. 장면은 이 뼈대에서만 나옵니다.

```markdown
# 결론 (1줄)
2029년, ○○동에 △△ 컨셉 빵집을 열면 월 □□만 원이 남고 ◇◇개월에 회수한다.

## 근거 1 — 왜 이 동네인가 (입지)
- 핵심 숫자 (출처, 기간, 단위) / 의외의 발견

## 근거 2 — 왜 이 가게인가 (타깃 → 공간 → 메뉴(시즌 한정) → 차별화)
- ...

## 근거 3 — 왜 남는가 (손익)
- ...

## 연결 점검 (컨셉의 일관성)
입지 → 타깃 → 공간 → 메뉴(시즌 한정) → 차별화 → 손익 — 각 화살표의 근거 한 줄씩
```

### ③ 시나리오 — `story/scenario.md`
논리 구조를 **장면 단위 대본**으로 바꿉니다. 장면마다 아래 표를 채웁니다.

| 시간 | 말할 것 (내레이션) | 화면의 주인공 1개 | 데이터 파일 | 모션 스타일 |
|---|---|---|---|---|
| 0:00–0:12 | "2029년, ○○동…" | 결론 숫자 | `story/logic.md` | 스플릿 플랩 디스플레이 |

- 내레이션은 한국어 기준 **1초에 약 5자** (2분 ≈ 600자)
- 기본 흐름 (결론부터):

  | 시간 | 장면 | 추천 모션 스타일 (아래 6번 목록) |
  |---|---|---|
  | 0:00–0:12 | **결론 먼저** — 동네·컨셉·월 이익 공개 | 스플릿 플랩 디스플레이, 키네틱 타이포그래피 |
  | 0:12–0:40 | 1. 입지 — 후보 비교 → 1위 공개, 2029년 변화 | 순위 카운트다운, 데이터 스토리 모션, 지도 경로, 타임라인 |
  | 0:40–0:55 | 2. 인테리어 — 타깃에서 나온 공간 | 아이소메트릭 익스플레이너, 블루프린트 |
  | 0:55–1:20 | 3. 메뉴 — 화제 디저트 주기와 우리의 한정 메뉴 전략, 가격 | 타임라인, 데이터 스토리 모션, 키네틱 타이포그래피 |
  | 1:20–1:45 | 4. 손익 — 돈의 흐름, 월 이익, 회수 기간 | 순서도, 숫자 카운터, 전후 비교(비관↔낙관) |
  | 1:45–2:00 | 결론 한 번 더 + 데이터 출처 | 엔드 카드 |

## 6. ④ 모션그래픽

### 모션 스타일 목록

참고: **[AI ROASTING — 모션 디자인](https://airoasting.com/motion-design.html#cat3)** — 스타일 40가지, 움직임 12원칙, 배경 음악 14가지. 스타일을 고르고 프롬프트를 복사하면 LLM이 **브라우저에서 바로 재생되는 HTML 영상**을 만들어 줍니다.

| 장면 성격 | 쓸 만한 스타일 |
|---|---|
| 결론·숫자 공개 | 스플릿 플랩 디스플레이, 숫자 카운터, 키네틱 타이포그래피 |
| 데이터·순위 비교 | 데이터 스토리 모션(막대 순위 경쟁), 순위 카운트다운 |
| 시간 흐름 (2029년 변화, 디저트 유행 주기) | 타임라인 |
| 위치·동선 | 지도 경로 |
| 공간·구조 (매장 평면) | 아이소메트릭 익스플레이너, 블루프린트, 라인 드로잉 |
| 과정·돈의 흐름 | 순서도 |
| 시나리오 비교 | 전후 비교 |
| 마무리 | 엔드 카드 |
| 따뜻한 분위기 (빵집 감성) | 수채화, 페이퍼 컷아웃, 클레이메이션 |

**통일성 규칙**
- 장면 형식은 달라도 **색 3개, 폰트 1~2개, 질감 1가지**는 영상 전체에서 하나로 맞춘다. 먼저 `video/style.md`에 정해 둔다
- **움직임 12원칙** 중 최소한 다음은 모든 장면에 적용: **연출**(장면당 주인공 하나만 강조), **천천히 시작하고 천천히 멈추기**(모든 이동에 가속·감속), **타이밍**(장면 분위기에 맞는 동작 길이). **과장**은 결론 장면에서 한 번만
- **배경 음악**은 1곡으로 통일 — 예: 어쿠스틱 팝, 보사노바(따뜻함), 미니멀 일렉트로닉(숫자·속도감)
- 데이터 차트의 숫자는 `for-video/` CSV 값을 **그대로** 쓰고, 화면 표기는 `UNITS.md`를 따른다

### 제작 방법

1. 장면마다 사이트의 프롬프트를 바탕으로 **장면별 HTML** 을 만든다 (`video/scenes/01_결론.html` …). 모든 그림은 코드로 그리고, 실제 가게 사진·로고는 쓰지 않는다
2. 장면들을 이어 붙인 **전체 HTML** 을 만들고 시나리오 시간에 맞춘다
3. **Playwright로 녹화** → ffmpeg로 mp4 변환
4. **내레이션(TTS):** `edge-tts` 파이썬 패키지 또는 브라우저 내장 음성 → ffmpeg로 영상·음악과 합치기, 자막 넣기

```
story/
├── logic.md        # ② 논리 구조
└── scenario.md     # ③ 장면별 시나리오
video/
├── style.md        # 색·폰트·질감·음악·움직임 원칙
├── scenes/         # 장면별 HTML
├── audio/          # 내레이션, 배경음
└── final.mp4
web/
└── index.html      # 30초 요약 웹페이지
```

### 웹페이지 — `web/index.html`
- 첫 화면: 결론 한 줄 + 핵심 숫자 3개 + 영상
- 아래로: 입지 점수표 → 컨셉 → 메뉴(시즌 한정) 전략 → 손익 → 출처
- 영상과 같은 `video/style.md` 색·폰트를 쓴다

## 7. 데이터 출처

### 서울 열린데이터광장 API 키 설정 (처음 1번)

1. 서울 열린데이터광장에서 발급받은 **일반 인증키**를 준비합니다.
2. **가장 쉬운 방법:** 쓰고 있는 LLM(에이전트)에게 이렇게 말합니다.
   > "내 서울 API 키는 `발급받은키`야. README대로 `.env`에 저장해 줘."

   에이전트가 레포 루트에 `.env`를 만들고 아래 한 줄을 넣습니다 (직접 만들어도 됩니다):
   ```
   SEOUL_OPENAPI_KEY=발급받은키
   ```
3. `.env`는 `.gitignore`에 들어 있어 커밋되지 않습니다. **키를 코드·README·커밋 메시지에 쓰지 마세요** (공개 레포일 수 있습니다).
4. 호출 형식: `http://openapi.seoul.go.kr:8088/{키}/json/{서비스명}/{시작}/{끝}/` (한 번에 최대 1,000건)

## 8. 폴더와 파일 형식

```
parts/
├── 0-research/              (1-location, 2-interior, 3-menu, 4-pnl도 같은 구조)
│   ├── findings.md          # 아래 템플릿
│   ├── SOURCES.md           # 출처 URL + 수집 날짜
│   ├── for-video/           # 영상에 쓸 재료: 차트 1개당 CSV 1개, 이미지
│   │   ├── 01_xxx.csv
│   │   └── UNITS.md         # 단위표 (필수)
│   ├── for-pnl.csv          # 4번 손익에 넘기는 입력값 (0~3번)
│   ├── data/                # 내려받은 원본·중간 데이터 (작은 파일만)
│   └── analysis.py (또는 .ipynb)
└── 1-location/scoring.csv   # 입지 점수 모델 (지표·가중치·원값·점수)
story/  video/  web/         # 6번 참고
```

**`for-video/` CSV 규칙:** UTF-8, 첫 줄은 한글 열 이름, 단위는 열 이름에 표기(예: `월임대료(만원/3.3㎡)`, `유동인구(명·분기누적)`), 차트 하나에 필요한 행만.

**`for-video/UNITS.md` 필수:** 파일마다 **단위, 뜻, 영상 화면 표기 예시, 기준 시점(현재값인지 2029년 환산값인지)** 을 표로 적습니다.

**`for-pnl.csv` 형식 (0~3번 → 4번):**

| 항목 | 값 | 단위 | 기준 | 근거 |
|---|---|---|---|---|
| 월임대료 | 18 | 만원/3.3㎡ | 2029 환산 | 2026Q2 값 × 최근 5년 연평균 상승률 3% (SOURCES.md 2번) |
| 매장면적 | 15 | 평 | — | 2번 평면안 |

- "기준" 열에 현재값인지 2029년 환산값인지 꼭 적습니다. 4번은 2029년 값만 계산에 씁니다.
- 위 숫자는 형식 예시일 뿐 실제 값이 아닙니다.

**`findings.md` 템플릿**

```markdown
# [1 입지선정] 한 줄 결론
예: ○○동 — 2028년 신규 역 개통과 대규모 입주로 2029년 아침 수요가 가장 클 동네

## 핵심 숫자 3개 (2029년 기준)
1. 값 (출처, 기간, 단위)

## 2029년에 왜 그런가
- (확정된 일정·추세 근거)

## 의외의 발견 (인사이트)
- 예상: ... → 실제 데이터: ... (출처, 기간, 단위)

## 영상에서 전할 메시지 (1~2문장)
...

## 영상 재료
- for-video/01_xxx.csv — 무엇을 보여주는지, 추천 모션 스타일
```

- 숫자는 **출처가 있는 것만** 씁니다. 추정치·환산값은 "추정", "2029년 환산"이라고 표시합니다.

## 9. MCP 실습 가이드

| MCP 서버 | 용도 | 쓰는 단계 |
|---|---|---|
| Filesystem (`@modelcontextprotocol/server-filesystem`) | 데이터·차트·장면 파일 읽고 쓰기 | 전체 |
| Fetch (`mcp-server-fetch`) | 서울 열린데이터 API, 웹페이지 가져오기 | 0, 1, 3, 4 |
| Playwright (`@playwright/mcp`) | golmok·데이터랩 화면 조회, 지도 캡처, **HTML 모션 녹화** | 0, 1, 7 |
| DuckDuckGo 검색 (`duckduckgo-mcp-server`) | 개발 계획·입주 일정·디저트 유행·재료 가격 뉴스 검색 | 0, 1, 3, 4 |

- **서울 API는 별도 MCP 없이** Fetch MCP나 Python으로 바로 부릅니다 (주소에 키만 넣으면 JSON이 옴).
- 패키지 이름·설정법은 바뀔 수 있으니 **실습 당일 안내나 공식 문서를 우선**하세요.

```

    "filesystem": { "command": "npx", "args": ["-y", "@modelcontextprotocol/server-filesystem", "<이 레포의 절대경로>"] },
    "fetch":      { "command": "uvx", "args": ["mcp-server-fetch"] },
    "playwright": { "command": "npx", "args": ["-y", "@playwright/mcp@latest"] },
    "ddg-search": { "command": "uvx", "args": ["duckduckgo-mcp-server"] }
  }
}
```

사전 설치: **Node.js 18+**, **Python 3.10+ / uv**, **ffmpeg**

## 10. 작업 관리

- 이 레포는 **양식(템플릿)** 입니다. 자기 작업은 **fork한 레포나 자기 레포**에 올리고, 원본 레포에는 push하지 않습니다.
- 단계가 하나 끝날 때마다 커밋해 두면, 4번에서 앞 단계로 돌아갈 때 편합니다.
- 100MB 넘는 파일(원본 영상 등)은 올리지 않습니다.

## 11. 보안·윤리 규칙

- API 키는 **`.env`에만** 두고 절대 커밋하지 않습니다. 실수로 올렸다면 바로 키를 재발급합니다.
- 개인정보(실명, 전화번호, 사람 얼굴 사진)는 수집·업로드하지 않습니다.
- 실제 가게의 사진·로고·메뉴판을 그대로 가져다 쓰지 않습니다. 디저트 유행 분석에서 가게 이름은 사실 확인용으로만 씁니다.
- 사이트에 무리가 가는 대량 자동 수집은 하지 않고, 제공되는 파일 다운로드를 우선합니다.
- 모든 수치에 출처와 날짜를 남기고, 영상 마지막에 출처를 표기합니다.

## 🤖 LLM 작업 지침

이 README를 읽은 LLM은 다음 순서로 도와주세요.

0. **목적:** 최종 목적은 **① 조사 → ② 논리 구조 → ③ 시나리오 → ④ 모션그래픽**이다. 조사는 논리 구조를 세우기 위해, 시나리오는 모션그래픽으로 옮기기 위해 한다. 단계를 건너뛰지 않는다(예: 논리 구조 없이 장면부터 만들지 않는다).
1. **평가 기준 우선:** 맨 위 [평가 기준](#평가-기준-모든-작업은-이-5가지를-채우도록-진행) 5가지(지표 논리성·근거 구체성·인사이트·컨셉 일관성·전달력)를 모든 단계에서 채운다. 단계를 마칠 때마다 5가지 중 무엇을 채웠고 무엇이 비었는지 사용자에게 짧게 점검해 보여 준다.
2. **개별 과제·대상:** 사용자 한 사람이 전부 한다. 대상은 **서울의 베이커리(제과점, `CS100005`)** 이며 **베이커리 카페가 아니다** — 카페형 좌석·음료 중심 기획으로 흐르지 않는다.
3. **진행 상황 확인:** `parts/`, `story/`, `video/`, `web/`에 무엇이 있는지 보고 어느 단계까지 왔는지 알려 준 뒤, 3번 순서대로 다음 단계를 진행한다. 처음이면 준비(API 키, MCP 연결, 2029년 환산 규칙)부터 함께 정한다.
4. **2029년 기준:** 2번 원칙을 지킨다. 지금 인기 있는 동네·메뉴를 그 자체로 근거 삼지 않는다. 디저트 유행은 **패턴(주기·공식)** 으로만 쓴다. 현재 값은 기준값으로만 쓰고, 2029년 값은 **기준 연도 값과 적용한 상승률을 밝혀 환산**한다. 미확정 계획은 "미확정"으로 표시한다.
5. **입지는 돈까지:** 1번 입지선정은 수요만 보지 않고, 0번의 컨셉별 표준 매장 모델로 **임대료·손님 수·동네 매출·면적·인테리어·설비 비용**까지 넣어 "가장 합리적인 동네 + 컨셉"을 고른다.
6. **데이터와 API 키:** 7번의 서울 열린데이터 API를 우선 쓴다. 접근 제한을 우회하지 않는다.
   - 레포 루트 `.env`에 `SEOUL_OPENAPI_KEY`가 없으면 사용자에게 키를 달라고 한다.
   - 사용자가 키를 주면 **레포 루트 `.env`에 `SEOUL_OPENAPI_KEY=키` 한 줄로 저장**한다(이미 있으면 그 줄만 바꾼다). 저장 후 `git check-ignore .env`로 커밋 제외인지 확인하고, 키로 1건만 호출해 작동하는지 확인한다.
   - 코드에서는 키를 항상 `.env`에서 읽는다. 키 값을 코드·다른 파일·커밋 메시지·답변에 다시 쓰지 않는다. 커밋 전에 키 값이 스테이징된 파일에 없는지 확인한다.
7. **약속된 형식:** 8번의 폴더 구조, `findings.md` 템플릿, `for-video/UNITS.md`, `for-pnl.csv` 형식을 따른다. 4번 손익은 0~3번의 `for-pnl.csv`를 읽어 계산하고, 값이 아직 없으면 "임시값"으로 표시해 진행한다.
8. **모션그래픽:** 6번의 스타일 목록과 통일성 규칙을 따른다. 먼저 `video/style.md`를 정하고, 시나리오의 장면마다 스타일을 하나씩 골라 HTML로 만든다. 숫자는 `for-video/` CSV 값을 그대로 쓴다.
9. **사실만:** 숫자를 지어내지 않는다. 모든 수치는 `SOURCES.md`에 URL과 수집 날짜를 남기고, 추정치는 "추정"이라고 표시한다.
10. **작게, 자주:** 한 단계씩 끝내고 결과를 보여 준 뒤 다음으로 넘어간다. 단계마다 커밋을 제안하고, push 전에는 사용자에게 확인받는다.
